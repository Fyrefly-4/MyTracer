# MyTracer 需求变更规则

> 适用基线：v0.1  
> 生效日期：2026-08-07  
> 目标：防止 Agent、架构或实现阶段自行扩大或改写产品范围

## 1. 基线文件

v0.1 的需求基线由以下文件共同组成：

1. [PRODUCT_REQUIREMENTS_V0.1.md](./PRODUCT_REQUIREMENTS_V0.1.md)：产品目标、需求、语义与验收；
2. [DECISIONS.md](./DECISIONS.md)：关键决定及其状态；
3. 本文：需求如何新增、调整、延期或删除。

用户文档用于解释产品，不得覆盖上述基线。

## 2. 核心规则

### CR-01：没有需求依据，不增加功能

“实现方便”“顺手”“常见产品都有”“以后可能需要”和“更完整”都不是新增范围的充分理由。

### CR-02：开放问题不是实现授权

待验证问题只能保持可调整，不能由 Agent 自行选取更复杂方案并加入 v0.1。

### CR-03：延期项不得混入 v0.1

延期项可以在设计文档中作为未来考虑单独标注，但不得成为当前模块、接口、页面或验收的必要组成部分。

### CR-04：实现不得偷换产品语义

不得因存储、统计或界面实现更简单而合并以下区别：

- 有所行动与达到目标；
- 主动休息与未进行；
- 未记录与未进行；
- 非强制意向与必须完成的行动；
- AI 建议与用户确认后的真实数据。

### CR-05：未来可扩展不等于提前实现

架构可以保持合理的可修改性，但不得为未知未来建设通用工作流、插件系统、动态数据模型、账号体系或复杂抽象层。

## 3. 哪些修改不需要产品批准

以下变更可以直接进行，但必须保持语义不变：

- 修正错别字、链接和格式；
- 补充不改变行为的说明或示例；
- 将重复描述整理得更清晰；
- 在已有 MUST/SHOULD 范围内选择具体实现方式；
- 增加测试、可观测性或错误处理，但不改变用户语义；
- 调整内部名称，只要用户可见概念和数据兼容性不受影响。

如无法判断是否改变语义，按需要批准的变更处理。

## 4. 哪些修改必须由用户确认

以下任何变更都必须先提出并获得用户明确确认：

- 新增、删除或修改 MUST；
- 将 SHOULD 升级为 MUST，或将 MUST 降级；
- 将延期项移入 v0.1；
- 新增用户可见核心概念、状态或主要视图；
- 改变目标、行动、例行、记录的语义；
- 改变五种例行记录状态及其统计含义；
- 将未记录自动视为未进行；
- 改变 AI 的触发方式、上下文边界或写入权限；
- 增加主动提醒、自动规划或自治 Agent 行为；
- 改变数据导出范围或用户删除能力；
- 删除或弱化验收场景；
- 因架构选择而要求用户改变已经确认的产品流程。

## 5. 变更提出格式

Agent 或设计者提出需求变更时，应使用以下最小格式：

```text
变更标题：
提出原因：
证据来源：真实使用 / 技术阻塞 / 需求矛盾 / 其他
受影响需求：FR-... / AC-... / D-...
建议变化：
是否扩大 v0.1 范围：是 / 否
对核心闭环的影响：
不变更的替代方案：
需要用户确认的问题：
```

没有真实证据时，应明确写为假设，不得包装为必须需求。

## 6. 变更流程

1. 发现矛盾、缺口或新需求；
2. 先判断能否在现有基线内解决；
3. 如涉及产品语义或范围，提交变更说明；
4. 用户确认接受、拒绝或延期；
5. 同步更新 PRD、`DECISIONS.md`、验收场景和变更记录；
6. 架构与任务文档重新核对受影响需求；
7. 修改完成前，不得把提议当作已批准需求实施。

## 7. 真实使用阶段的变更原则

Demo 使用期允许记录大量想法，但不立即全部加入产品。

一个新需求优先进入后续版本的条件是：

- 在真实使用中重复出现；
- 明确阻碍核心闭环；
- 现有轻量路径无法合理解决；
- 带来的价值高于新增概念和记录成本。

单次灵感、竞品已有功能或技术展示机会，默认进入候选记录，不直接改变基线。

## 8. Agent 行为要求

所有参与产品、架构、实现、测试和评审的 Agent 必须：

- 开始工作前阅读 PRD、`DECISIONS.md` 和本文；
- 用需求编号说明设计或实现依据；
- 明确区分需求、设计选择和未来建议；
- 发现超范围内容时停止扩展并指出；
- 发现 MUST 冲突时提出阻塞，不得自行选择一方；
- 不得以“最佳实践”为理由覆盖用户已经确认的语义；
- 不得将待验证问题提前固化为复杂架构；
- 在交付前检查新增内容是否改变范围。

## 9. v0.1 冻结解除条件

仅在以下情况之一发生时调整 v0.1 基线：

- 发现两个 MUST 无法同时满足；
- 核心流程存在无法继续设计或实现的真实阻塞；
- 用户明确要求调整；
- Demo 真实使用证据表明当前决定阻碍核心价值。

除此之外，新想法默认进入后续版本候选。
