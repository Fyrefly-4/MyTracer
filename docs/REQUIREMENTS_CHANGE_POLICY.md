# MyTracer 需求变更规则

> 适用范围：持续迭代；保留 v0.1 产品语义基线\
> 初始基线日期：2026-08-07；持续迭代规则更新：2026-10-23\
> 目标：防止 Agent、架构或实现阶段自行扩大或改写产品范围

## 1. 基线文件

v0.1 的需求基线由以下文件共同组成：

1. [PRODUCT_REQUIREMENTS_V0.1.md](./PRODUCT_REQUIREMENTS_V0.1.md)：产品目标、需求、语义与验收；
2. [DECISIONS.md](./DECISIONS.md)：关键决定及其状态；
3. 本文：需求如何新增、调整、延期或删除。

用户文档用于解释产品，不得覆盖上述基线。用户明确提出或批准的功能、UX 调整是该项工作的执行依据，不需要再提交一次形式审批；仍有效的语义和决定继续适用，已批准变化只更新受影响部分。

## 2. 核心规则

### CR-01：没有需求依据，不增加功能

“实现方便”“顺手”“常见产品都有”“以后可能需要”和“更完整”都不是新增范围的充分理由。

### CR-02：开放问题不是实现授权

待验证问题只能保持可调整，不能由 Agent 自行选取更复杂方案并加入 v0.1。

### CR-03：延期项不得混入 v0.1

这是原 v0.1 Demo 的范围约束，不是后续明确授权演进的永久禁令。未经请求的延期项不得顺手成为当前模块、接口、页面或验收的必要组成部分。

### CR-04：实现不得偷换产品语义

不得因存储、统计或界面实现更简单而合并以下区别：

- 有所行动与达到目标；
- 主动休息与未进行；
- 未记录与未进行；
- 非强制意向与必须完成的行动；
- AI 建议与用户确认后的真实数据。

### CR-05：未来可扩展不等于提前实现

架构可以保持合理的可修改性，但不得为未知未来建设通用工作流、插件系统、动态数据模型、账号体系或复杂抽象层。

## 3. 哪些修改不需要产品批准

以下变更可以直接进行，但必须保持语义不变：

- 修正错别字、链接和格式；
- 补充不改变行为的说明或示例；
- 将重复描述整理得更清晰；
- 在已有 MUST/SHOULD 范围内选择具体实现方式；
- 增加测试、可观测性或错误处理，但不改变用户语义；
- 调整内部名称，只要用户可见概念和数据兼容性不受影响。

如无法判断是否超出已授权范围，说明具体疑点并只暂停受影响部分；继续其他独立工作。

## 4. 哪些修改必须由用户确认

以下变化需要用户明确确认其范围；当前请求已明确包含的变化无需重复批准，未说明的重大连带影响仍须讨论：

- 新增、删除或修改 MUST；
- 将 SHOULD 升级为 MUST，或将 MUST 降级；
- 将延期项移入 v0.1；
- 新增用户可见核心概念、状态或主要视图；
- 改变目标、行动、例行、记录的语义；
- 改变五种例行记录状态及其统计含义；
- 将未记录自动视为未进行；
- 改变 AI 的触发方式、上下文边界或写入权限；
- 增加主动提醒、自动规划或自治 Agent 行为；
- 改变数据导出范围或用户删除能力；
- 删除或弱化验收场景；
- 因架构选择而要求用户改变已经确认的产品流程；
- 所有数据库 schema 迁移（包括非破坏性迁移）；
- 新增或升级依赖。

一般功能授权不隐含批准迁移、新依赖或权限扩展；若请求已明确批准这些具体操作，不重复确认。Git、发布及外部操作授权仍遵循 [AGENTS.md](../AGENTS.md)。

## 5. 变更提出格式

普通已授权改动在 PR 中简要说明“问题 → 改法 → 验证”即可。FR、AC、D 编号可作为有帮助的引用，不是每次工作的必填项。

重大语义、数据、安全或架构取舍需保留聚焦的设计/决定依据：受影响行为、关键风险、替代方案、确认范围与验证方法。按问题需要展开，不要求固定九字段表单。没有真实证据时明确标为假设。

## 6. 变更流程

1. 确认请求、相关现状和受影响范围；已明确授权的部分直接推进。
2. 发现未授权的重大影响或尚未解决的矛盾时，讨论该部分；不把提议当作批准。
3. 实现并运行与风险相称的检查，在 PR 中记录结果和限制。
4. 只更新实际受影响的需求、决定、说明或验收场景；不要求每次同步全部 PRD、DECISIONS、任务及历史账本。重要决定应可追溯，历史事实不追改。

## 7. 真实使用阶段的变更原则

Demo 使用期允许记录大量想法，但不立即全部加入产品。

以下是评估未获授权的新建议时的参考，不是用户明确请求的前置审批门槛：

- 在真实使用中重复出现；
- 明确阻碍核心闭环；
- 现有轻量路径无法合理解决；
- 带来的价值高于新增概念和记录成本。

单次灵感、竞品已有功能或技术展示机会，默认进入候选记录，不直接改变基线。

## 8. Agent 行为要求

本规则维护产品语义与变更批准边界，不激活开发阶段流程。是否使用 Txxx 合同、阶段 Skill、证据账本或阶段门，按根目录 `AGENTS.md` 的显式启用边界判断；普通请求不因遵守本规则而进入上述流程。

所有参与产品、架构、实现、测试和评审的 Agent 必须：

- 涉及产品行为、范围或验收语义时，按需阅读 PRD、`DECISIONS.md` 和本文的相关部分；无关工作不要求全量阅读；
- 涉及产品行为时说明请求与行为依据，相关需求编号按需引用；
- 明确区分需求、设计选择和未来建议；
- 发现超范围内容时停止扩展并指出；
- 发现 MUST 冲突时提出阻塞，不得自行选择一方；
- 不得以“最佳实践”为理由覆盖用户已经确认的语义；
- 不得将待验证问题提前固化为复杂架构；
- 在交付前检查新增内容是否改变范围。

## 9. v0.1 冻结的历史背景

v0.1 Demo 阶段采用以下基线调整条件，保留用于理解历史决定：

- 发现两个 MUST 无法同时满足；
- 核心流程存在无法继续设计或实现的真实阻塞；
- 用户明确要求调整；
- Demo 真实使用证据表明当前决定阻碍核心价值。

持续迭代按本文现行授权和记录规则处理；这些历史条件不额外限制用户明确批准的演进。未获授权的新想法仍是建议。
