# E4 · 阅读先听见自己的记录

共同基线 `bfd46c08d8fd9403ac7ec3b9abe1a3d187a2f6ea`；产品起源 `a02175e6cf598f08f3c4d053cccb2cf85d42816c`。独立于 E1/E2/E3，不合并或发布，保留可逆原型供父级比较。

假设：Progress 展开记录后先读自己写下的简述/笔记，再读理解与困惑，会更像回看自己的经历。记录册本来已经这样排序，此处只移动现有 RecordedText 槽位，不新造阅读系统。整个原文槽位（包括原有“记录中的下一步”和其历史说明）移到理解/困惑之前；原文字体、内容、字段语义、重试和加载状态保持不变。Progress 显式开启顺序参数；共享组件的默认顺序与 Review 调用保持基线。

默认仍折叠，只在展开且 hasRecordedText 时读取；已有理解不等待原文。长笔记继续用 RecordNote 的 >500 字符或 >8 行折叠，未新增状态、预取、固定高度或布局占位。关闭、重新查询与晚到响应隔离沿用原机制。

强反例：原文异步到达时，原文槽位从一行“正在读取”变成多行简述/备注，下面的理解/困惑可能跳离正在看的位置。长笔记即使默认折叠，最长简述仍可显著占高；用户手动展开长笔记后也会把理解压到下面。空/读取失败时先看加载或错误而非已有理解，可能更烦。无需架构改造就能做此槽位实验，但不能因此把风险当成已解决。

父级复现与否决：

1. Progress 同一记录带短简述、短笔记、理解和困惑，展开，确认原文先于解释；Review 展开同样资料，顺序仍为理解/困惑→原文。
2. 用长简述和 >500 字笔记比较默认折叠和完整笔记展开，确认原文字体/折叠未变；检查理解是否被埋住。
3. 原文为空、只有理解、返回空文字、错误/重试时，对照基线可读性，不能把未加载当成空内容。
4. 延迟原文响应，先读已出现的理解，然后放行响应；在 820×650 及正常桌面尺度比较。`progress-record-text.e2e.test.ts` 增加长简述延迟场景，输出 before/after 截图和理解标题坐标 JSON，仅留本地 Playwright 附件。该坐标是变化证据，不是用户体验通过门槛。
5. 若阅读理解/困惑时发生明显跳走，建议否决或保持待定；不靠阻塞理解、提前读取、巨高容器或改服务补救。

本地验证与限制：lint/types/build、定向格式/diff 检查及相关单元测试结果由 PR 正文/交接绑定 head。原生测试为 Windows 专用、chromiumSandbox=true，当前容器不具备相同验收环境，未执行，不禁用沙箱。上述布局代价是源码推断，实际幅度、焦点/滚动与审美比较待父级 native；未声称真实用户研究或交互通过。
